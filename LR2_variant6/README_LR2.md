# ЛР2 — верификация софт-процессора RISC-V, вариант 6

## 1. Как выбран вариант

В методичке в каждом самостоятельном задании по 6 вариантов.
По указанному правилу:

```text
6 % 6 + 1 = 1
```

Поэтому для бригады/варианта 6 фактически получаются:

1. **Задание 1 — быстрая сортировка (Quick Sort)**.
2. **Задание 2 — Wishbone `wb_ram`**.

Это важно: здесь выполняется не строка 6 таблицы, а строка 1 после вычисления по формуле.

---

## 2. Что сделано

Проект основан на приложенном `PicoSoC_Wishbone`.
Исходная память программ `wb_ram.v` сохранена: её убирать нельзя, потому что из неё
PicoRV32 читает `firmware.mem`.

К системе добавлен третий Wishbone slave — дополнительная RAM для задания 2.

Карта адресов:

| Диапазон | Назначение |
|---|---|
| `0x0000_0000 ... 0x0000_FFFF` | исходная RAM программы/данных |
| `0x1001_0000 ... 0x1001_0FFF` | GPIO |
| `0x1002_0000 ... 0x1002_0FFF` | дополнительная Wishbone RAM задания 2 |

В `Pico_SoC.v` число ведомых устройств кроссбара увеличено с 2 до 3.

## 3. Подготовка среды

Работа рассчитана на Linux/Ubuntu или WSL Ubuntu.
RISC-V toolchain установите по методичке. Скрипт сначала ищет компилятор здесь:

```text
~/riscv-gnu-toolchain/installed-tools/bin/riscv32-unknown-elf-gcc
```

Если его там нет, используется `riscv32-unknown-elf-gcc` из `PATH`.

Для симуляции нужен Verilator:

```bash
sudo apt update
sudo apt install verilator gtkwave build-essential python3
```

Перейдите в корень проекта:

```bash
cd LR2_variant6
```

## 4. Задание 1 — Quick Sort через Verilator

Прошивка находится в:

```text
firmware/firmware_quicksort.c
```

В ней задан массив из 20 целых 32-битных значений, в том числе отрицательных.
После сортировки процессор последовательно пишет результат в GPIO:

- `0x10010000` — очередное отсортированное значение;
- `0x10010004` — его номер от 1 до 20.

Запуск одной командой:

```bash
./run_quicksort.sh
```

Скрипт:

1. компилирует C-код для RISC-V;
2. создаёт `firmware.mem`;
3. при первом запуске собирает модель Verilator;
4. запускает PicoRV32;
5. C++-тестбенч проверяет все 20 отсортированных значений.

Ожидаемый конец журнала:

```text
PASS: quicksort result is correct
```

Также создаётся:

```text
verilator.vcd
```

Его можно открыть:

```bash
gtkwave verilator.vcd
```

Полезные сигналы для демонстрации:

- `gpio`, `gpio1`;
- `wb_adr_pico`;
- `wb_dat_o_pico`, `wb_dat_i_pico`;
- `wb_we_pico`;
- `wb_cyc_pico`, `wb_stb_pico`, `wb_ack_pico`.

## 5. Максимальный размер массива

В стартовом файле `firmware/firmware.S` указатель стека устанавливается в:

```text
16368 = 0x3FF0
```

То есть стек начинается почти у границы 16 KiB и растёт вниз.
Поэтому максимальный локальный массив зависит не только от объёма RAM, но и от:

- размера программы;
- служебных данных в стеке;
- кода, который сгенерировал конкретный GCC;
- используемого алгоритма.

Для экспериментального определения максимума подготовлены:

```text
firmware/firmware_array_limit.c
find_max_array.sh
```

Запуск:

```bash
./find_max_array.sh
```

Скрипт меняет `ARRAY_SIZE`, перекомпилирует прошивку и бинарным поиском находит
максимальный размер локального массива `int`, который проходит проверку в вашей
реальной версии RISC-V toolchain.

Полученное число нужно записать в отчёт. Это корректнее, чем заранее вписывать
одно фиксированное число: оно может немного отличаться при другом компиляторе.

Для основной демонстрации в Quick Sort всё равно используется только 20 элементов,
что выполняет требование методички "не более 30".

## 6. Задание 2 — дополнительный Wishbone RAM

Для теста используется:

```text
firmware/firmware_wb_ram_test.c
```

Алгоритм очень простой:

1. процессор записывает 16 известных 32-битных слов в RAM по адресу `0x10020000`;
2. затем читает их обратно;
3. сравнивает каждое значение;
4. если всё совпало, записывает `1` в GPIO;
5. при ошибке записывает `0`, а в `GPIO+4` — номер ошибочного слова.

### Предварительная проверка в Verilator

```bash
./run_wb_ram_test.sh
```

Ожидаемый результат:

```text
PASS: processor wrote and read the additional Wishbone RAM
```

### Проверка на ПЛИС

Сначала соберите прошивку:

```bash
./prog_make.sh firmware_wb_ram_test.c
```

После этого в корне появится `firmware.mem`.

Для DE10-Lite подготовлен верхний модуль:

```text
de10_lite_top.v
```

В Quartus нужно добавить в проект как минимум:

```text
de10_lite_top.v
Pico_SoC.v
picorv32.v
wb_ram.v
wb_ram_ip.v
wb_gpio.v
wbxbar.v
addrdecode.v
skidbuffer.v
firmware.mem
```

Top-Level Entity:

```text
de10_lite_top
```

Назначения физических выводов лучше взять из уже рабочего DE10-Lite проекта или
официального шаблона платы: в этот комплект намеренно не записаны непроверенные pin
locations.

После прошивки:

- нажмите/отпустите `KEY[0]` для сброса;
- `LEDR[0] = 1` — тест RAM завершился успешно;
- `LEDR[0] = 0`, а `LEDR[9:1] != 0` — номер слова, на котором возникло несовпадение.

## 7. Откуда взялся `wb_ram_ip.v`

В исходном PicoSoC уже есть модуль с именем `wb_ram`, и он является памятью программы.
Удалять или заменять его нельзя.

Поэтому дополнительный блок задания называется `wb_ram_ip` и имеет совместимые
параметры/порты 32-битного Wishbone RAM. Это позволяет одновременно оставить
исходную память программы и подключить вторую RAM как отдельное периферийное устройство.

Если преподавателю принципиально нужен именно исходный файл из репозитория
Alex Forencich, выполните:

```bash
./get_official_wb_ram.sh
```

Скрипт скачает официальный `rtl/wb_ram.v` и изменит только имя модуля на
`wb_ram_ip`, чтобы не было конфликта имён. После этого остальные файлы проекта
менять не требуется.

## 8. Что показать на защите

Для задания 1 достаточно показать:

- исходный неотсортированный массив;
- функции `partition()` и `quicksort()`;
- успешный лог Verilator;
- в GTKWave последовательность отсортированных значений на `gpio`;
- результат `find_max_array.sh` и объяснить связь со стеком `0x3FF0`.

Для задания 2:

- новый адрес `0x1002_0000`;
- изменение `NS: 2 -> 3` в `Pico_SoC.v`;
- третий набор Wishbone-сигналов в кроссбаре;
- цикл записи и чтения в `firmware_wb_ram_test.c`;
- PASS в Verilator;
- на ПЛИС `LEDR[0] = 1`.
